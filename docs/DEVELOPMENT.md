# Development Workflow

## Setup

Follow `AGENTS.md` for the verified base commands. A typical local setup is:

```bash
composer install
cp .env.example .env
php artisan key:generate
php artisan migrate --seed
php artisan storage:link
npm install
```

Run the application with:

```bash
composer dev
```

## Before Changing Code

1. Read `AGENTS.md` and `docs/*` relevant to the task.
2. Inspect the owning module and nearby tests.
3. Check `git status` and do not revert unrelated changes.
4. Identify route names, table keys, view namespaces, and persisted contracts that
   must remain compatible.
5. Prefer the smallest correct change.

## Composer Path Packages

The root `composer.json` defines a wildcard path repository for `modules/*` with
symlinks enabled. Edit package source under `modules/*`; never edit the copy under
`vendor/figure-admin/*`.

When adding a package:

1. Add `modules/<Module>/composer.json`.
2. Add PSR-4 autoloading and Laravel provider discovery metadata.
3. Require `figure-admin/shared: dev-main`.
4. Require `figure-admin/host: ^1.0` if the package imports `App\...`.
5. Add the root `require` and path version mapping.
6. Update Composer metadata and run package discovery.

Typical commands:

```bash
composer update figure-admin/<package> --with-dependencies
composer dump-autoload
php artisan package:discover --ansi
```

Avoid unrelated dependency upgrades. Inspect `composer.lock` after every package
metadata change.

Do not manually register package providers in `bootstrap/providers.php`.

## Adding an Admin Resource

1. Choose the owning feature package.
2. Add the controller and Form Request under the module.
3. Add a concrete Shared Form and Table only when required.
4. Add module routes with explicit controller classes and existing middleware
   conventions.
5. Register the table key explicitly in the module provider.
6. Register or update the menu entry with a stable unique key.
7. Use module-owned views extending `shared::` layouts.
8. Add focused route, registry, view, and behavior tests.

## DataTable Development

When a displayed column uses relation notation, test the exact AJAX order/filter
request generated by DataTables.

For relation sorting that creates joins:

```php
->usingQuery(Model::query()
    ->select('base_table.*')
    ->where('base_table.status', ...))
```

Never leave `id`, `status`, or other duplicated columns unqualified in a joined
query.

Do not expose exception messages in HTTP responses.

## Frontend and Vite

Active Vite entries are declared in `vite.config.js`:

- Shared admin JavaScript and SCSS
- Booking calendar JavaScript and SCSS
- Communications email-preview JavaScript and SCSS
- Dashboard JavaScript and SCSS

Add every new page-level entry explicitly. Feature assets stay in their owner
module. Generic UI behavior belongs in Shared.

Use the established Blade `@vite`, page script/style, or stack conventions. Do
not hardcode source paths that are absent from the production manifest.

The root application installs Shared browser peer dependencies. Preserve the
documented jQuery/Bootstrap globals until all consumers are migrated.

## Database Changes

- Put migrations in the root database directory while domain ownership remains
  host-based.
- Review foreign-key delete behavior before changing account or profile deletion.
- Use transactions for multi-write flows.
- Add factories or deterministic test helpers for new integration behavior.
- Do not repair data by adding compatibility code unless persisted data requires
  it and the migration strategy is explicit.

## Documentation Changes

Update the relevant `docs/*` file in the same change when modifying:

- Package boundaries or dependencies
- Module ownership
- Route or registry contracts
- Shared public APIs or frontend hooks
- Build/test commands
- Known limitations or operational requirements
